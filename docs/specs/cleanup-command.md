# `cleanup` コマンド仕様

`/cc-portfoliokit:cleanup` の機能仕様。実装プロンプトは [`commands/cleanup.md`](../../commands/cleanup.md) を参照。

---

## 1. 責務

`cleanup` は **手書きで編集された入力 Markdown の構造ドリフトを直す** 補助コマンド。`init` でも `create` でもない、3 本目のメインフロー外コマンドです。

対象ファイルは **入力側 Markdown 3 つ + 顔写真関連** のみ:

- `./config.md`
- `./career/profile.md`
- `./career/work-history.md`
- `./assets/` 配下 ── 顔写真ファイルとの整合性チェック用

`./portfolio.html` は **対象外**。HTML の再生成は `create` の責務。

### 設計の根本ルール

- **読み書き両用**。ただし **1 件ずつ確認** モードで進める。一括書き換え禁止。
- **HTML には触らない**。`portfolio.html` を `Edit` も `Write` もしない。
- **削除より「残す」を優先**。判定に迷う行は触らずスキップ候補に倒す。
- **手書き内容を勝手に書き換えない**。値の意味を変える修正は禁止。構造の修正に限定。
- `init` 未実行のときは **案内のみ** で終了 ── `guide` と同じ守り方。

---

## 2. 起動フロー

```
Step 1. 状態判定        — 入力 Markdown 3 つが揃っているか
Step 2. 全件スキャン     — 問題リスト ($ISSUES) を構築
Step 3. サマリー提示     — ファイル別 / 種別別の件数を出す
Step 4. 1 件ずつ確認     — 各 $ISSUE について「直す / スキップ / 残り全部 OK / 中断」
Step 5. 完了報告        — 直した件数 / スキップ件数 / 残課題
```

### 2.1 Step 1 — 状態判定

`config.md` / `career/profile.md` / `career/work-history.md` の 3 つの存在を確認する。

- **1 つでも欠ける** → 「`/cc-portfoliokit:init` を先に実行してください」と案内して終了。何も書き換えない。
- **3 つ揃っている** → Step 2 へ。

### 2.2 Step 2 — 全件スキャン

各ファイルを `Read` し、§3 の検出ルールに沿って `$ISSUES` を組み立てる。

`$ISSUE` は次の構造で保持する:

```
- id:        連番 (#1, #2, ...)
- file:      対象ファイルパス
- line:      該当行番号 (近似で OK)
- category:  STRUCTURE / EMPTY_BLOCK / FORMAT / PARENS / ASSET_MISMATCH / WORK_HISTORY
- severity:  high / mid / low
- summary:   1 行で表す問題内容
- before:    現在の該当箇所 (短い抜粋、3〜10 行程度)
- after:     提案する修正後の姿
- action:    EDIT (該当箇所を置換) / DELETE_BLOCK (見出しブロックごと削除) / ADVISE (自動修正せず助言のみ)
```

スキャン中に `Edit` してはいけない。**スキャンと修正を分離** すること。

### 2.3 Step 3 — サマリー提示

ユーザーに次の形でサマリーを出してから、レビュー開始の同意を取る。

```
🧹 cleanup スキャンが完了しました。

検出された問題: $TOTAL 件
  - config.md:         $C 件
  - career/profile.md: $P 件
  - career/work-history.md: $W 件
  - assets/ との不整合: $A 件

内訳:
  high  (構造の必須項目): $H 件
  mid   (見やすさ・ルール違反): $M 件
  low   (任意の整形): $L 件

これから 1 件ずつ確認していきます。各件で「直す / スキップ / 残り全部 OK / 中断」を選べます。
始めてもいいですか? (Yes / No)
```

`$TOTAL = 0` の場合は「綺麗な状態です。何もする必要はありません」と報告して終了。

### 2.4 Step 4 — 1 件ずつ確認

`$ISSUES` を **high → mid → low** の順、同 severity 内では **file 順** で 1 件ずつ提示する。

```
─ 問題 $i / $TOTAL ─
ファイル: $file:$line
種類: $category ($severity)
内容: $summary

【今の書き方】
  $before

【こう直そうと思います】
  $after

どうしますか?
  1) 直す
  2) スキップ (このまま残す)
  3) 残り全部 まとめて Yes (推奨しません)
  4) 中断 (ここまでの修正は保持)
```

- **1) 直す**: `$action` に従って `Edit` を 1 回実行 → 直後に対象ファイルを **再 `Read`** して破壊が無いか確認 → 次の問題へ。
- **2) スキップ**: 何もせず次の問題へ。
- **3) 残り全部 OK**: 残る問題を **high のみ自動修正、mid / low は手を付けず終了** ── 安全側に倒す。
- **4) 中断**: そこまでの修正は保持して Step 5 へ。
- **Edit 失敗** が出たら **即座に中断**。ユーザーに状況を報告し、それ以上自動修正は試みない。

### 2.5 Step 5 — 完了報告

```
✅ cleanup 完了

直した: $FIXED 件
スキップ: $SKIPPED 件
残った: $REMAINING 件 (high $RH / mid $RM / low $RL)

次のおすすめ:
  - 残課題がある場合: もう一度 /cc-portfoliokit:cleanup を叩くか、
    Markdown を直接開いて手で直してください
  - 修正があった場合: /cc-portfoliokit:create で portfolio.html を作り直すと
    新しい内容が反映されます
```

## 3. 検出ルール

検出ルールは **5 カテゴリ + work-history 専用ルール** の 6 ブロックに分ける。

### 3.1 STRUCTURE — 構造の必須項目

`severity: high`。

| ファイル | 必須見出し | 欠けた場合の action |
|---|---|---|
| `config.md` | `## サイトタイトル` / `## テーマカラー` | ADVISE ── 値が無いと HTML 生成が壊れる旨を伝え、テンプレートからのコピペを促す |
| `career/profile.md` | `## 氏名` / `## 職業` / `## キャリア総年数` | ADVISE ── 同上 |
| `career/work-history.md` | `## <名称>` ブロックが 1 件以上 | ADVISE ── 0 件のときは「職歴を 1 件は書いてください」と促す |

> 値の中身までは検査しない。**見出しが存在するか** だけを確認する。

### 3.2 EMPTY_BLOCK — 中身が空の見出しブロック

`severity: mid`。

仕様: `init` の規約で **入力なしフィールドは `### 見出し` ごと省略** することになっている。手で編集した結果、見出しだけ残って値が空になっているブロックを検出する。

- 検出対象: `## 〇〇` / `### 〇〇` の **直下が空行のみ、または次の見出しまで実質空** のブロック
- **コメント `<!-- ... -->` だけ残っているのは「空」とみなさない** ── コメントには編集ヒントが入っているため
- `action: DELETE_BLOCK` ── 該当見出し行から **次の同レベル以上の見出しの手前まで** を削除する提案
- ただし、`config.md` の `## サイトタイトル` / `## テーマカラー` のように **「無いと困る必須項目」** は §3.1 で別途検出される。EMPTY_BLOCK ではなく STRUCTURE の ADVISE として扱う

> サンプル値 ── たとえば `your-email@example.com` ── は「空」ではない。値があるなら触らない。

### 3.3 FORMAT — 書式の乱れ

`severity: mid` か `low`。

| 検出内容 | severity | action |
|---|---|---|
| `## 見出し` 直下に空行が無い (見出しと値の間が密着) | mid | EDIT ── 1 行空行を挿入 |
| `## 名称` ブロックの間の空行が 1 行しかない (推奨は 2 行) | low | EDIT ── 空行を 1 行追加 |
| 行末の半角スペース | low | EDIT ── 削除 |
| ファイル末尾の連続空行が 3 行以上 | low | EDIT ── 1 行に揃える |
| HEX カラーが `#` + 3 桁 / 6 桁の英数字でない | mid | ADVISE ── 「`#4F46E5` のような形式で書いてください」と提示 |
| `## 表示言語` の値が `ja` / `en` 以外 | low | ADVISE ── 想定値を案内するのみ |

### 3.4 PARENS — 補足の `( )` 書き

`severity: low`。

CLAUDE.md ルール: ドキュメント・対話文では `( )` で補足説明を書かない。ユーザーの入力 Markdown は **配色 / 表現の柔軟性が高い** ため、検出は **値の本文だけに限定** する。

- **対象外** (検出しない):
  - 見出し行そのもの ── 例: `## 自己紹介 (About)` ── にある `( )`
  - `<!-- -->` 内のコメント
  - 期間表記の `2020-04 〜 2023-03 (3 年)` のような付加情報 ── これは情報量があるので触らない
  - 半角の URL や数式に含まれる `( )`
- **対象** (検出する):
  - `### やったこと` / `### 成果` などの本文中で「`(例: 〇〇)`」「`(参考: 〇〇)`」のような **明示的な補足記号** が含まれる場合のみ
- `action: ADVISE` ── 「地の文で書き直しませんか?」と提案するだけ。**自動置換しない**。ユーザーの文章を勝手に書き換えると意味が変わるリスクが高いため

### 3.5 ASSET_MISMATCH — 顔写真の不整合

`severity: mid`。

- `config.md` の `## 顔写真のファイル名` に書かれているパス ── 例: `assets/photo.jpg` ── が **実ファイルとして存在しない**
  - `action: ADVISE` ── 「assets フォルダにファイルが見つかりません。置き忘れていませんか?」
- `assets/` に画像ファイルがあるが、`config.md` から参照されていない
  - `severity: low` / `action: ADVISE` ── 「使われていないファイルがあります。意図したものですか?」

> ファイルサイズや形式の検査は深追いしない。`create` 側で扱う警告と重複させない。

### 3.6 WORK_HISTORY — 職歴ファイル専用

`severity: high` か `mid`。

| 検出内容 | severity | action |
|---|---|---|
| `### 種別` が無いエントリ | high | ADVISE ── 「本業 / 副業 / 活動 のいずれかを書いてください」 |
| `### 種別` の値が `本業` / `副業` / `活動` のいずれでもない | high | ADVISE ── 「3 つから選んでください」 |
| 1 つの `## 名称` 内に `### 種別` が **複数** ある | high | ADVISE ── 「種別は 1 つだけにしてください」 |
| `### 期間` が無いエントリ | mid | ADVISE ── 「期間を書くことをおすすめします」 |
| `### やったこと` が無い、または値が空 | mid | ADVISE ── 「やったことを 1 つは書いておくと HTML 側で見栄えが良くなります」 |
| `### やったこと` / `### 成果` が箇条書きでない (`- ` で始まる行が無い) | low | ADVISE ── 「箇条書きにすると HTML で読みやすく出ます」 |

> WORK_HISTORY は **値の妥当性** に踏み込むカテゴリだが、**自動修正しない**。すべて ADVISE。

## 4. 対話設計の方針

- **専門用語を避ける**。「ドリフト」「リファクタリング」「正規化」のような語は対話文に出さない。代わりに「**ちょっと崩れているところ**」「**整える**」のような優しい言い回しを使う。
- 各問題の提示では **「今の書き方」と「こう直そうと思います」を必ず両方見せる**。before/after が無い変更はしない。
- ユーザーの答えが曖昧 ── 例えば「うーん」 ── な場合は **スキップに倒す**。勝手に直さない。
- 「残り全部 まとめて Yes」を選ばれても、**mid / low には触らない**。安全側を死守。
- 中断後、ファイルが壊れた状態で終わることが無いように、Edit 失敗時はその時点で **必ず立ち止まる**。

---

## 5. 共通制約

- **HTML / portfolio.html / templates/ / docs/ / skills/** を一切書き換えない。
- 性別 `gender` には触れない ── `init` 同様、扱わない方針。
- コメント `<!-- ... -->` は **常に保持** する。中の編集ヒントが消えるとユーザーが困る。
- `## 見出し` 行そのもの ── 名前部分 ── は書き換えない。値の置換 / 空ブロックの削除 / 空行の追加削除 のみ。
- 並行セッション対策: `Edit` 直前にもう一度 `Read` し、最新状態に対して差分を取る。会話前半で読んだ記憶だけで Edit しない。
- `Bash` の使用は **`ls` 系の読み取り** に限定。`mv` / `rm` / `cp` は使わない。

---

## 6. 想定されるエラー / エッジケース

| 状況 | 対応 |
|---|---|
| `init` 未実行で 3 ファイル無し | 案内のみ。何もせず終了 |
| ファイル 1〜2 個欠け | `init` の補完を促して終了。残っているファイルを勝手に手直ししない |
| パース不可能なほど壊れている | スキャンで気づいた時点で「自動で扱えないので手で開いて直してください」と案内して中断 |
| Edit の old_string が見つからない | その問題だけ FAILED として記録し、次の問題に進む。失敗が 3 件続いたら全体を中断 |
| 並行セッションが同じファイルを書き換えた | 再 Read で気づいたら、その問題はスキップ扱いにしてユーザーに通知 |
| ユーザーが対話途中で「やめる」 | そこまでの修正は保持。何が反映されたかを報告 |

---

## 7. このコマンドが扱わないこと

- **HTML の再生成** ── `create` の仕事です。`cleanup` 完了後にユーザー自身が `create` を叩く流れ。
- **値の意味を変える書き換え** ── 例えば「TypeScript」を「JavaScript」に書き換える、のような変更はしない。
- **新しい項目の追加提案** ── 「居住地も書いたらどうですか?」のような提案はしない。`init` / `create` のヒアリング責務と分離する。
- **テンプレートの再展開** ── `templates/*.md` からファイルを再生成することはしない。それは `init` の上書きモードの仕事。

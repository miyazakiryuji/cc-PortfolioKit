§番号は元の `hearing-command.md` のものをそのまま維持しています。

`hearing` の実装プロンプト ([`commands/hearing.md`](../../commands/hearing.md)) が次のタイミングでこのファイルを `Read` する想定:

- Step 2 ループメニューで「4) これまでに入れた本業・副業・活動を直す」を選ばれたとき → §9 を参照
- Step 4 書き出しを実行するとき → §11 を参照
- Step 5 完了報告を表示するとき → §12 を参照

## 9. 編集サブメニュー (Step 2 の 4 番)

「4) これまでに入れた本業・副業・活動を直す」を選ばれたとき。**2 段階方式** で、件数が増えても圧迫感が出ないようにします。

### 9.1 第 1 段階 ── カテゴリ選択

まず「どのカテゴリのものを直したいか」を尋ねます。

```
どの種類を直しますか?

  1) 本業 ── 登録 $M 件
  2) 副業 ── 登録 $S 件
  3) 活動 ── 登録 $A 件
  c) 戻る
```

`c` または「キャンセル」「戻る」と入力されたら Step 2 のメインメニュー (`hearing-command.md` §5.1) に戻ります。0 件のカテゴリも表示しますが、選ばれたら「このカテゴリにはまだ何も入っていませんよ」と案内して 9.1 に戻ります。

### 9.2 第 2 段階 ── エントリ選択

カテゴリが選ばれたら、そのカテゴリのエントリだけを **ローカル番号** で一覧表示します。

```
どの本業を直しますか?

  1) 株式会社サンプル (2020-04 〜 現在)
  2) 株式会社例示 (2018-04 〜 2020-03)

  c) 戻る
```

`c` で 9.1 に戻ります。番号を入力したら 9.3 へ。

### 9.3 第 3 段階 ── 1 件分の編集モード

エントリが 1 件選ばれたら、そのエントリの **どの項目を直すか** を尋ねます。**破壊的な操作 (削除・種別変更) は別メニュー (`7) その他`) に隔離** して、誤操作を減らします。

**本業の編集メニュー:**

```
「株式会社サンプル」のどこを直しますか?

  1) 会社名
  2) 期間
  3) 役職
  4) ふだんやっていたこと
  5) 全体の成果
  6) プロジェクトを追加 / 削除 / 編集

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

**副業の編集メニュー:**

```
「〇〇社 技術アドバイザー」のどこを直しますか?

  1) 案件名 / クライアント名
  2) 期間
  3) 立場
  4) ふだんやっていたこと
  5) 使ったツール・スキル
  6) 成果

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

**活動の編集メニュー:**

```
「〇〇 Meetup 運営」のどこを直しますか?

  1) 活動名 / イベント名
  2) 期間
  3) 立ち位置
  4) ふだんやっていたこと
  5) 関連スキル・道具
  6) 規模感・成果

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

`1)〜6)` の項目を選ばれたら、対応する質問を 1 問だけ聞き直して、メモリ上のデータを書き換える。書き換えが終わったら 9.3 のメニューに戻る (続けて他の項目を直すユーザーもいるため)。`c` で 9.2 に戻る。

### 9.3.x 「その他」サブメニュー

`7) その他` が選ばれたら次を表示します。

```
このエントリに対してできる「その他の操作」です。よく考えてから選んでください。

  1) このエントリ自体を削除する (取り消し不可)
  2) 種別を変える (本業 ↔ 副業 ↔ 活動)
  c) 戻る
```

`1)` を選ばれたら §9.5 (削除) へ、`2)` を選ばれたら §9.4 (種別変更) へ、`c` で 9.3 に戻る。

### 9.4 「種別を変える」の挙動

「その他」サブメニュー (§9.3.x) の `2) 種別を変える` が選ばれたら:

```
「○○」の種別を変えます。新しい種別はどれですか?
  1) 本業
  2) 副業
  3) 活動
```

- **本業 ↔ 副業 ↔ 活動 の変更時**: 構造が変わる可能性があるので、共通項目 ── 名称 / 期間 / 役職 (or 立場 or 役割) / やったこと相当 ── は引き継ぐ。本業のみにある「全体の成果」と「PJ」は、本業 → それ以外への変更で **メモリから削除** する。副業・活動 → 本業への変更時は、空のまま始まる。
- ユーザーには **PJ の件数と PJ 名一覧を見せてから** 確認を入れる ── 「PJ 情報」と言うだけだと、ユーザーは何が消えるかピンと来ないため。たとえば:

  ```
  「○○」を 副業 に変えます。
  ただしこのエントリには、いま 3 件のプロジェクトが入っています:
    - 〇〇プロダクト開発
    - △△ システム導入
    - □□ リプレース PJ

  種別を変えると、上のプロジェクトはぜんぶ消えてしまいます。
  よろしいですか? (はい / いいえ)
  ```

### 9.5 1 件削除の挙動

「その他」サブメニュー (§9.3.x) の `1) このエントリ自体を削除する` が選ばれたら:

```
「○○」を削除します。よろしいですか? (Yes / No)
```

`Yes` ならメモリから削除して 9.2 のエントリ選択メニュー (該当カテゴリの一覧) に戻る。`No` なら何もせず 9.3 の編集メニューに戻る。

## 11. Step 4 — 書き出し

メモリ上のエントリリストを `career/work-history.md` に書き出します。

### 11.1 既存ファイルとの関係

- **`work-history.md` が存在しない場合**: `init` 未実行 ── Step 0 でチェックして案内のみで終了するべき (`hearing-command.md` §13 参照)。
- **存在する場合**: `hearing-command.md` §13.1 の「既存エントリの上書き警告」で同意を取った上で、既存内容を全面置換する。ヒアリングで入れたエントリを **メモリ上のリストで全置換** する形。
- **テンプレ末尾の編集ヒント (コメント) は再書き出し** する。手編集の助けになるため。
- **0 件で終了した場合は書き出しを行わない** ── 既存ファイルを保護する。これは Step 5 (§12) の挙動と合致させる。

### 11.2 書き出し形式 (本業)

```markdown
## 株式会社サンプル

### 種別

本業

### 期間

2020-04 〜 現在

### 役職

シニアソフトウェアエンジニア

### 業務内容

- バックエンド開発リード
- マネジメント

### 全体の成果

- 組織のリリース頻度向上

### プロジェクト: 〇〇プロダクト開発

#### 使ったツール・スキル

TypeScript, AWS

#### 成果

- レスポンス時間 50% 改善

### プロジェクト: △△ システム導入

#### 使ったツール・スキル

Python, GCP

#### 成果

- MAU 10 万達成
```

### 11.3 書き出し形式 (副業)

```markdown
## 〇〇社 技術アドバイザー

### 種別

副業

### 期間

2023-06 〜 現在

### 役職

業務委託 (技術アドバイザー)

### やったこと

- 開発チームの設計レビュー
- 採用面接の技術評価

### 使ったツール・スキル

Node.js, AWS

### 成果

- 採用候補者のミスマッチ率を半減
```

### 11.4 書き出し形式 (活動)

```markdown
## 〇〇 Meetup 運営

### 種別

活動

### 期間

2021-01 〜 現在

### 役職

主催 / 運営メンバー

### やったこと

- 月 1 回の勉強会企画・運営
- スポンサー獲得

### 使ったツール・スキル

イベント運営 / 司会進行

### 成果

- 累計参加者 500 名超
```

### 11.5 共通の書き出しルール

- **見出しと値の間は空行 1 つ**。手編集しやすく、`cleanup` の検出ルールにも合致する。
- **エントリとエントリの間は空行 2 つ**。視認性のため。
- **任意項目で値が無い場合は、その `### ` ブロックごと出力しない**。「役職: (なし)」のような空欄を残さない。
- **本業の `### プロジェクト: <名前>` ブロックが 0 件のとき**: その本業エントリは PJ ブロックを書き出さない。会社単位の項目だけ書く。
- **副業・活動の見出しは内部的に統一**: 副業の「立場」も活動の「自分の役割」も、Markdown 上は `### 役職` として保存する。`### 使ったツール・スキル` / `### 成果` も同じ見出しで統一。これは `create` / `cleanup` のパースをシンプルに保つため。質問文だけカテゴリに合わせて言い換える ([`hearing-categories.md`](./hearing-categories.md) §7 / §8 参照)。
- **書き出すブロックにインラインコメントは付けない**: 「`### 役職` をなんて書けばいい?」と迷う手編集ユーザーのケアは、`templates/work-history.md` のファイル冒頭コメントとひな型コメントに任せる。`hearing` が書き出す各エントリには注釈コメントを足さない。理由は、編集中に削除されたり、コメントだらけで読みにくくなるのを避けるため。
- **テンプレ末尾の「新しいエントリを追加するときのひな型」コメント**: そのまま再書き出しする。手編集の助けになる。

### 11.6 書き出しの動作

1. メモリ上のエントリリストを `$ORDER` で並べ替え (`$ORDER` は `hearing-command.md` §10 で決まる)。
2. ファイル冒頭 (`# 職歴・副業・活動` のタイトルとファイル先頭コメント) を保持。
3. エントリ部分を全置換。
4. ファイル末尾のひな型コメント (`<!-- ■ 新しいエントリを追加するときのひな型 -->`) を保持。
5. `Write` で全体を書き出す。

> **`Write` の前に `Read` し直す**: 並行セッション対策。会話前半で読んだ記憶のまま `Write` しない。差分が予期しない大きさなら、ユーザーに確認を入れる。

## 12. Step 5 — 完了報告

最後に温かいトーンで完了を伝えます。下記が画面に出す確定形。

```
✅ 経歴のヒアリング、おつかれさまでした!

書き込んだ件数 (合計 $TOTAL 件):
  本業 $M 件:
    1) 株式会社サンプル (2020-04 〜 現在)
    2) 株式会社例示 (2018-04 〜 2020-03)
  副業 $S 件:
    1) 〇〇社 技術アドバイザー (2023-06 〜 現在)
  活動 $A 件:
    1) 〇〇 Meetup 運営 (2021-01 〜 現在)

次のステップ:
  /cc-portfoliokit:create

このコマンドで、入れていただいた経歴と、別途用意するプロフィールから HTML を作ります。
出来上がりがどんな雰囲気になるか、見てみてのお楽しみです。
```

`$TOTAL = 0` のときは、件数の振り返り部分を省略して短めに:

```
✅ ひとまず終わりにします。
   経歴は 0 件のままなので、書き換えはしませんでした。

次のステップ:
  - 経歴を追加したくなったら、もう一度 /cc-portfoliokit:hearing を実行してください。
  - 経歴なしでも HTML を作りたい場合は /cc-portfoliokit:create で進められます。
```

### 12.1 アイコン画像未配置のリマインド

`hearing-command.md` §4.2.2 で `assets_missing = true` フラグが立っていた場合、完了報告の **末尾** に次のリマインドを 1 回だけ表示します。

```
🖼 アイコン画像のお知らせ
./assets/ にまだ画像が入っていないので、create する前に 1 枚入れておくと
ポートフォリオの仕上がりがぐっと良くなります。
顔写真でも、似顔絵でも、お気に入りの 1 枚でも、お好きなものを。
```

### 12.2 完了報告の書き方ルール

- 件数の振り返り部分の `本業 $M 件:` / `副業 $S 件:` / `活動 $A 件:` は、**0 件のカテゴリは出力しない** ── 「該当なしならこのブロックごと省略」という仕様メモが画面にそのまま流れ込まないよう、ここで明文化しておく。
- 完了報告内の絵文字は `✅` と `🖼` の 2 つだけ。`🎉` のような派手な絵文字は使わない (CLAUDE.md「絵文字を控えめに」)。
- 「楽しみですね」のような感情を押し付ける言い回しは避け、「お楽しみです」のような引いた言い方にする。

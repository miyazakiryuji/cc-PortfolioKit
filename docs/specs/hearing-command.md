# `hearing` コマンド仕様

`/cc-portfoliokit:hearing` の機能仕様。実装プロンプトは [`commands/hearing.md`](../../commands/hearing.md) を参照。

---

## 0. 適用前提

この仕様書は次のファイル群と **同時に** 適用される前提で書かれています。`hearing` だけを先行して入れても、`init` / `create` / `cleanup` / `guide` / `templates/` / `skills/` 側が古いままだとシステム全体が壊れます。実装着手前に、下表の更新箇所を **すべて把握** してから書き始めてください。

| 同時更新が必要なもの | 更新内容 (要約) |
|---|---|
| `commands/init.md` | Step 3 / Step 4 のヒアリング部分を削除。`init` は「ファイル作成 + アイコン画像配置とプロフィール記入の促し + これからの流れの案内」だけにする |
| `CLAUDE.md` | 「メインの 2 本 + 補助の 2 本」を「メインの 3 本 (init / hearing / create) + 補助の 2 本 (cleanup / guide)」に書き換え。ディレクトリ構成図にも `hearing.md` を追加 |
| `commands/guide.md` | Step 1 のサマリーを 3 コマンド体制に。Step 3 ブランチ C に「経歴 0 件のときは `hearing` を案内する」分岐を追加 |
| `commands/create.md` および `docs/specs/create-command.md` | `career/work-history.md` のパース仕様を更新 ── 本業の `### プロジェクト: <名前>` ブロックと `#### 使ったツール・スキル` / `#### 成果` のサブ見出しを取り出せるように。`### 使用技術` → `### 使ったツール・スキル` の表記揺れも吸収 |
| `commands/cleanup.md` および `docs/specs/cleanup-command.md` | `WORK_HISTORY` 検出ルールを更新 ── 本業エントリは `### やったこと` の代わりに `### 業務内容` を必須候補にする。新しい見出し ── `### 業務内容` / `### 全体の成果` / `### プロジェクト: <名前>` / `#### 使ったツール・スキル` / `#### 成果` ── の存在チェックも追加 |
| `skills/portfolio-design/SKILL.md` | 本業エントリの PJ ループを HTML に出力するレンダリングルールを追記 |
| `templates/work-history.md` | サンプルを新構造 ── 本業の二段構造、`### 使ったツール・スキル` への名称変更 ── に書き換え |
| `templates/profile.md` | `## キャリア総年数` ブロックを削除 ── `hearing` も `init` も聞かないため |
| `templates/config.md` | `## 連絡先` の `### サブ項目` を主要 SNS 10 個弱に拡張。Email / X / GitHub / Instagram / Facebook / LinkedIn / YouTube / TikTok / note / Website を想定 |
| `docs/手順書.md` | 新コマンド体系の流れ ── init → assets 配置 + profile.md 編集 → hearing → create ── に書き換え |

> **実装は段階的に**: いきなり全部を変えると衝突しやすい。論理単位ごとに 1 コミットずつ切って、CLAUDE.md の「修正時の必須ルール」に従って進めること。

## 1. 責務

`hearing` は **経歴 ── 本業・副業・活動 ── を対話形式で 1 件ずつ集めて `career/work-history.md` に書き出す** コマンドです。

`init` でファイルを作ったあと、`create` で HTML を生成する前の **「中身を埋める」** フェーズを担当します。プロフィール ── 氏名・職業・連絡先・自己紹介・趣味など ── は **ヒアリングしません**。それらは `career/profile.md` と `config.md` をユーザー自身に手で編集してもらう想定です。

### 設計の根本ルール

- **経歴だけを聞く**。プロフィールには触らない。
- **ループ式メニュー**。本業 → 副業 → 活動 の固定順序ではなく、ユーザーが「次に何を追加するか」を毎回選ぶ。
- **本業だけ二段構造**。会社単位の情報 + プロジェクト単位のループ。副業・活動はフラット。
- **編集も同じコマンドで**。新規追加だけでなく「すでに入れた経歴を直す」もメニューから呼べる。
- **温かい言葉で話しかける**。質問文・選択肢・案内文すべてを「親しい先輩がカフェで話しかけてくれる感じ」のトーンで。`CLAUDE.md` の「文体のトーン」ルールを厳守。

## 2. 用語の定義

| 用語 | 意味 |
|---|---|
| **本業** | フルタイムで所属している / していた会社・組織 |
| **副業** | 業務委託・フリーランス・個人開発・顧問など、本業以外でお金が動く取り組み |
| **活動** | イベント運営・コミュニティ活動・OSS・登壇・執筆など、お金が直接動かない取り組みも含む |
| **エントリ** | `## 名称` ブロック 1 つに対応する 1 件分の経歴 ── 本業 1 社、副業 1 案件、活動 1 件など。対話文では「エントリ」とは呼ばず、「本業」「副業」「活動」と並列で書く |

## 3. 起動フロー (全体像)

```
Step 1. アイコン画像チェック   — assets/ に画像があるか確認、無ければユーザーに選択を委ねる
Step 2. ループメニュー         — 「次に何を追加するか」を選んでもらう。終了するまでループ
  Step 2-a. カテゴリ別の 1 件分ヒアリング (本業 / 副業 / 活動)
  Step 2-b. 編集サブメニュー (すでに入れたものを直す)
Step 3. 並び順の質問           — 新しい順 / 古い順
Step 4. 書き出し              — career/work-history.md に全エントリを書く
Step 5. 完了報告              — 件数の振り返り + create コマンドへの誘導
```

---

## 4. Step 1 — 入り口の案内

> **意図**: `hearing` の入り口で「これから何があるか」と「アイコン画像が入っているか」を確認します。所要時間の見通しが立ち、入り口で離脱しにくくなるための小さな安全網。

### 4.1 これからの流れ案内

最初に下記の **温度感メッセージ** を一度だけ表示します。書き出しの前に「全体像」と「所要時間目安」が見えるよう、心理的負荷を下げる狙いです。

```
【これから何をするか】
経歴 ── 本業・副業・活動 ── を 1 件ずつ、対話で聞いていきます。
お名前や自己紹介などのプロフィールはここでは触らないので、安心してくださいね。

🕐 だいたいの所要時間の目安
  本業 1 社あたり ── 3〜5 分くらい
  副業・活動 1 件あたり ── 1〜2 分くらい

途中でやめても、書きたい分だけ書いて終わって大丈夫です。
それじゃ、始めていきましょう。
```

### 4.2 アイコン画像チェック

`./assets/` 配下に画像ファイルが 1 つでもあるかを `Bash` で確認します。

#### 4.2.1 画像が 1 枚以上ある場合

何も尋ねず Step 2 に進みます。後段の `create` コマンドが `assets/` 配下の画像を自動で拾うので、ファイル名のヒアリングはここでは不要です。

#### 4.2.2 画像が 1 枚も無い場合

ユーザーに次の声がけをして、選択肢を出します。**おすすめは `1)` 続ける** ── 入り口でいきなり「やり直し」を強いると、慎重派の人ほど詰まるためです。

```
あれ、./assets/ にまだ画像が入っていないみたいです。
ポートフォリオの「顔」になるアイコン画像 ── 顔写真でも、似顔絵でも、お気に入りの 1 枚でも大丈夫 ── があると、より素敵な仕上がりになります。

進め方を選んでください:
  1) このまま経歴のヒアリングを始める。画像はあとで足してね、というおすすめパターン
  2) いったんやめて、画像を入れにいく
```

- **1) を選ばれた場合**: 「了解です。画像はあとで入れて大丈夫」と一言添えて、メモリ上に `assets_missing = true` フラグを立てて Step 2 へ進む。このフラグは Step 5 (§12) の完了報告で「画像まだ入れていませんね、忘れないでね」と思い出させるために使う。
- **2) を選ばれた場合**: 「待ってますね。画像を入れたら、もう一度 `/cc-portfoliokit:hearing` を叩いてください」と伝えて即座に終了。

#### 4.2.3 ./assets/ フォルダそのものが存在しない場合

ユーザーに次を伝えて終了します。

```
あれ、./assets/ フォルダがまだ無いみたいです。
最初に /cc-portfoliokit:init を実行して、ファイルとフォルダを用意してもらえますか?
```

## 5. Step 2 — ループメニュー

`hearing` の心臓部です。**ユーザーが「終了する」を選ぶまでループ** します。

### 5.1 メニュー表示

毎ターン、次のメニューを表示します。**初回 (全カテゴリ 0 件) のときは枕詞** を 1 行添えて、0 件のプレッシャーを下げます。

**初回 (全カテゴリ 0 件) の表示:**

```
これから経歴を 1 件ずつ集めていきますね。
最初は何を追加します?

  ▼ 登録状況
    本業: 0 件
    副業: 0 件
    活動: 0 件

  1) 本業を追加
  2) 副業を追加
  3) 活動を追加
  5) いったん終了する

  ※ 番号でも、「やめる」「終わり」のような言葉でも大丈夫です
```

> 初回はまだ何も入力していないので、`4) これまでに入れた...を直す` は表示しません。中身が無いものを「直す」のは意味がないため。

**2 周目以降 (どれかのカテゴリが 1 件以上) の表示:**

```
次に何を追加しますか?

  ▼ 登録状況
    本業: $MAIN_COUNT 件
    副業: $SIDE_COUNT 件
    活動: $ACTIVITY_COUNT 件

  1) 本業を追加
  2) 副業を追加
  3) 活動を追加
  4) これまでに入れた本業・副業・活動を直す
  5) 終了する

  ※ 番号でも、「やめる」「終わり」のような言葉でも大丈夫です
```

`$MAIN_COUNT` / `$SIDE_COUNT` / `$ACTIVITY_COUNT` は、メモリ上に保持しているエントリリストの件数です。0 件のカテゴリも省略せず並べる ── 進捗が見える方がモチベーションになります。

### 5.2 メニューの分岐

| 選択 | 進む先 |
|---|---|
| 1) 本業を追加 | §6 の本業 1 件分のヒアリング → 終わったら 5.1 に戻る |
| 2) 副業を追加 | §7 の副業 1 件分のヒアリング → 終わったら 5.1 に戻る |
| 3) 活動を追加 | §8 の活動 1 件分のヒアリング → 終わったら 5.1 に戻る |
| 4) これまでに入れた本業・副業・活動を直す | §9 の編集サブメニューへ → 終わったら 5.1 に戻る (初回は表示しない) |
| 5) 終了する | §5.3 のゼロ件チェック → Step 3 へ |

選択肢の番号以外の文字 ── 「終わり」「やめる」「キャンセル」など ── が入力された場合も、`5)` 相当として扱います。メニュー末尾の「※ 番号でも、〜 言葉でも大丈夫です」の一言は、その挙動をユーザーに明示するための案内です。

### 5.3 終了時のゼロ件チェック

`MAIN + SIDE + ACTIVITY = 0` の状態で「5) 終了する」を選ばれたら、確認ダイアログを 1 回挟みます。

```
本業・副業・活動とも 0 件のままですが、本当に終了しますか?
  はい  → そのまま終了して書き出し処理へ進む
  いいえ → メニューに戻る
```

「はい」なら Step 3 へ、「いいえ」なら 5.1 のメニューに戻ります。

> **0 件で終了したときの挙動**: `work-history.md` のエントリ部分は空のまま書き出します。テンプレ末尾の編集ヒント (コメント) は残します。

## 6. 本業 1 件分のヒアリング (二段構造)

本業は **「会社単位」と「プロジェクト単位」の二段構造** です。会社の中で複数の PJ を担当して、PJ ごとにツールも成果も違う ── という現実に合わせています。

### 6.1 会社単位の質問 (5〜6 問)

1 つずつ短く、温かいトーンで聞きます。下に書いてあるのは **そのまま画面に出す質問文の確定形** です。仕様メモ ── たとえば「内部で `YYYY-MM` に正規化」のようなもの ── は **絶対に画面に出さない**。

```
1. 会社の名前を教えてください
   → 自由記入。空欄は不可

2. いつから働き始めましたか?
   たとえば「2020-04」「2020/04」「2020 年 4 月」みたいに、年月が分かれば書き方はお任せです。
   → 自由記入

3. そのお仕事、いまも続いていますか?
   1) はい、いまも続いています
   2) いいえ、もう辞めました
   → 2) を選んだ場合のみ次の質問

3-a. ちなみに、いつまで在籍していましたか?
   書き方は始めたときと同じで大丈夫です。
   → 自由記入

4. 肩書きや役職はありましたか?
   たとえば「ソフトウェアエンジニア」「マネージャー」「アートディレクター」「課長」など。
   特になければ「なし」と答えてもらえれば飛ばします。
   → 自由記入

5. その会社でふだんやっていたことを 3〜5 個くらいで教えてください
   1 つずつ言ってもらってもいいし、まとめて言ってもらっても OK。箇条書きに整理します。

6. 会社全体で言える代表的な成果があれば教えてください
   ここで聞いているのは「特定のプロジェクトではなく、その会社にいた期間全体で言える代表的な成果」です。
   このあと印象に残ったプロジェクトを別途聞くので、そちらでは PJ ごとの成果を伺います。
   思いつかなければ「特になし」で大丈夫です。
   たとえば「売上 2 倍」「受賞歴」「制度設計の主担当」「全社の DX 推進」のようなもの。
```

> **質問順序の番号と Markdown 見出し順序の関係**: 上の `1.〜6.` は「ユーザーに聞く順番」です。Markdown 上の `### 役職 / ### 業務内容 / ### 全体の成果` 見出しの並び順とは独立しています (書き出し形式は §11.2 参照)。
>
> **内部処理メモ (仕様書側だけで使う言葉)**: 日付の自由入力は内部で `YYYY-MM` に揃えてから記録する。ただし「正規化」「フォーマット」「YYYY-MM」のような語は **ユーザー画面の質問文には絶対に出さない**。
>
> **5. の質問文の補足**: 質問文上の表現は「ふだんやっていたこと」で本業・副業・活動とも統一する (§7 / §8 と整合)。書き出し時の Markdown 見出しは本業のみ `### 業務内容`、副業・活動は `### やったこと` ── これはパース都合で、ユーザーには見えない区別。

### 6.2 PJ ループへの誘導

会社単位の質問が終わったら、PJ ループへの導入を聞きます。

```
このお仕事の中で、印象に残ったプロジェクトや案件はありますか?
  1) はい、書きたい
  2) いいえ、スキップで
```

`1)` を選ばれたら PJ ループへ、`2)` を選ばれたらこの本業 1 件分の入力は完了。Step 2 (5.1 のメニュー) に戻ります。

### 6.3 PJ 単位のループ (3 問 × N 件)

PJ 1 件あたり次を聞きます。質問文は下の確定形をそのまま画面に出す想定。

```
PJ 1 件目について教えてください。

a. プロジェクト名や案件名を教えてください
   公開できないお仕事は「〇〇業界の決済システム PJ」のような匿名表記でも大丈夫です。
   → 自由記入

b. このプロジェクトで使ったツール・スキル、ぱっと思い出せるものがあれば教えてください
   思いつかなければ「特になし」で大丈夫です。
   職業によって言い回しが変わる場合があるので、デザイナーなら「使ったツール」、営業なら「扱った商材や業界」のような形でも OK。

c. このプロジェクトでの成果があれば教えてください
   数字で言えるもの、評価されたこと、学んだことなど、書きやすい形で。
   思いつかなければ「特になし」で大丈夫です。
```

1 件入力が終わったら、続けるか確認します。

```
このお仕事で、もう 1 件 PJ を追加しますか?
  1) はい、追加する
  2) いいえ、終わり
```

`1)` ならループ続行、`2)` なら本業 1 件分が完了して Step 2 のメニューに戻ります。

> b. と c. の **「思いつかなければ『特になし』で大丈夫」** の一文は、CLAUDE.md の「補足の書き方ルール」に沿って `(任意)` のような `( )` 表記を使わずに任意性を伝える書き方。`(任意)` を画面に出さないこと。

### 6.4 本業 1 件分のデータ構造 (メモリ上)

メモリ上ではこんな構造で保持します。

```yaml
type: "本業"
name: "株式会社サンプル"
period: "2020-04 〜 現在"          # 内部で正規化済み
role: "シニアソフトウェアエンジニア"  # 空欄可
業務内容:
  - "バックエンド開発リード"
  - "マネジメント"
全体の成果:                        # 任意。スキップなら null
  - "組織のリリース頻度向上"
projects:
  - name: "〇〇プロダクト開発"
    tools: "TypeScript, AWS"        # 任意
    achievements:                   # 任意
      - "レスポンス時間 50% 改善"
  - name: "△△ システム導入"
    tools: "Python, GCP"
    achievements:
      - "MAU 10 万達成"
```

## 7. 副業 1 件分のヒアリング (フラットな 6 問)

副業は **「案件単位 = 1 件」** がふつうなので、本業のような二段構造は不要。フラットに 6 問。下記が画面に出す確定形です。

```
1. 案件名やクライアント名を教えてください
   たとえば「〇〇社」「個人開発の △△」「IT スタートアップ A 社」のような形で。
   公開できないお仕事は匿名でも大丈夫です。
   → 自由記入

2. いつから関わっていましたか?
   書き方は「2022-04」「2022/04」「2022 年 4 月」みたいに、年月が分かれば OK。
   → 自由記入

2-a. それ、いまも続いていますか?
   1) はい、いまも続いています
   2) いいえ、もう終わりました
   → 2) を選んだ場合のみ次を聞く

2-b. (2-a で「いいえ」のとき) ちなみに、いつまで続けていましたか?
   → 自由記入

3. その副業、どんな立場で関わっていました?
   1) 個人で受けた仕事 (業務委託・フリーランス)
   2) 顧問・アドバイザー
   3) 社外取締役
   4) 個人開発・個人プロジェクト
   5) その他 (一言で書いてもらいます)

4. その案件でふだんやっていたことを 1〜3 個くらい教えてください
   1 つずつでも、まとめてでも OK。

5. 使ったツール・スキル、ぱっと思い出せるものがあれば教えてください
   思いつかなければ「特になし」で大丈夫です。

6. 公開できる成果があれば教えてください
   NDA などで書けないものは無理に書かなくて大丈夫。
   思いつかなければ「特になし」で大丈夫です。
```

> **質問文上の `(自由記入)` のような `( )` 補足は画面に出さない**。CLAUDE.md の補足の書き方ルールに沿って、ユーザーに見せる質問文・選択肢ラベルからは `( )` 表記を排除する。
>
> **「業務委託」と「フリーランス」を 1 つに統合**: 税務上ほぼ同じで、書く側がどっちで答えるか迷うのを防ぐため。差別化したい人は `5) その他` で「業務委託 (準委任)」のように書いてもらう。

### 7.1 副業 1 件分のデータ構造 (メモリ上)

```yaml
type: "副業"
name: "〇〇社 技術アドバイザー"
```

## 9. 編集サブメニュー (Step 2 の 4 番)

「4) これまでに入れた本業・副業・活動を直す」を選ばれたとき。**2 段階方式** で、件数が増えても圧迫感が出ないようにします。

### 9.1 第 1 段階 ── カテゴリ選択

まず「どのカテゴリのものを直したいか」を尋ねます。

```
どの種類を直しますか?

  1) 本業 ── 登録 $M 件
  2) 副業 ── 登録 $S 件
  3) 活動 ── 登録 $A 件
  c) 戻る
```

`c` または「キャンセル」「戻る」と入力されたら Step 2 のメインメニューに戻ります。0 件のカテゴリも表示しますが、選ばれたら「このカテゴリにはまだ何も入っていませんよ」と案内して 9.1 に戻ります。

### 9.2 第 2 段階 ── エントリ選択

カテゴリが選ばれたら、そのカテゴリのエントリだけを **ローカル番号** で一覧表示します。

```
どの本業を直しますか?

  1) 株式会社サンプル (2020-04 〜 現在)
  2) 株式会社例示 (2018-04 〜 2020-03)

  c) 戻る
```

`c` で 9.1 に戻ります。番号を入力したら 9.3 へ。

### 9.3 第 3 段階 ── 1 件分の編集モード

エントリが 1 件選ばれたら、そのエントリの **どの項目を直すか** を尋ねます。**破壊的な操作 (削除・種別変更) は別メニュー (`7) その他`) に隔離** して、誤操作を減らします。

**本業の編集メニュー:**

```
「株式会社サンプル」のどこを直しますか?

  1) 会社名
  2) 期間
  3) 役職
  4) ふだんやっていたこと
  5) 全体の成果
  6) プロジェクトを追加 / 削除 / 編集

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

**副業の編集メニュー:**

```
「〇〇社 技術アドバイザー」のどこを直しますか?

  1) 案件名 / クライアント名
  2) 期間
  3) 立場
  4) ふだんやっていたこと
  5) 使ったツール・スキル
  6) 成果

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

**活動の編集メニュー:**

```
「〇〇 Meetup 運営」のどこを直しますか?

  1) 活動名 / イベント名
  2) 期間
  3) 立ち位置
  4) ふだんやっていたこと
  5) 関連スキル・道具
  6) 規模感・成果

  7) その他 ── このエントリを削除する、種別を変える
  c) 戻る
```

`1)〜6)` の項目を選ばれたら、対応する質問を 1 問だけ聞き直して、メモリ上のデータを書き換える。書き換えが終わったら 9.3 のメニューに戻る (続けて他の項目を直すユーザーもいるため)。`c` で 9.2 に戻る。

### 9.3.x 「その他」サブメニュー

`7) その他` が選ばれたら次を表示します。

```
このエントリに対してできる「その他の操作」です。よく考えてから選んでください。

  1) このエントリ自体を削除する (取り消し不可)
  2) 種別を変える (本業 ↔ 副業 ↔ 活動)
  c) 戻る
```

`1)` を選ばれたら §9.5 (削除) へ、`2)` を選ばれたら §9.4 (種別変更) へ、`c` で 9.3 に戻る。

### 9.4 「種別を変える」の挙動

「その他」サブメニュー (§9.3.x) の `2) 種別を変える` が選ばれたら:

```
「○○」の種別を変えます。新しい種別はどれですか?
  1) 本業
  2) 副業
  3) 活動
```

- **本業 ↔ 副業 ↔ 活動 の変更時**: 構造が変わる可能性があるので、共通項目 ── 名称 / 期間 / 役職 (or 立場 or 役割) / やったこと相当 ── は引き継ぐ。本業のみにある「全体の成果」と「PJ」は、本業 → それ以外への変更で **メモリから削除** する。副業・活動 → 本業への変更時は、空のまま始まる。
- ユーザーには **PJ の件数と PJ 名一覧を見せてから** 確認を入れる ── 「PJ 情報」と言うだけだと、ユーザーは何が消えるかピンと来ないため。たとえば:

  ```
  「○○」を 副業 に変えます。
  ただしこのエントリには、いま 3 件のプロジェクトが入っています:
    - 〇〇プロダクト開発
    - △△ システム導入
    - □□ リプレース PJ

  種別を変えると、上のプロジェクトはぜんぶ消えてしまいます。
  よろしいですか? (はい / いいえ)
  ```

### 9.5 1 件削除の挙動

「その他」サブメニュー (§9.3.x) の `1) このエントリ自体を削除する` が選ばれたら:

```
「○○」を削除します。よろしいですか? (Yes / No)
```

`Yes` ならメモリから削除して 9.2 のエントリ選択メニュー (該当カテゴリの一覧) に戻る。`No` なら何もせず 9.3 の編集メニューに戻る。

## 10. Step 3 — 並び順の質問

ループを抜けたあと、書き出し前に並び順を尋ねます。

```
職歴を並べますね。新しい順 / 古い順、どちらにしますか?

  1) 新しい順 (おすすめ)
  2) 古い順
```

選ばれた順序を `$ORDER` として保持。**カテゴリ内** の並び替えに使います。カテゴリ間 ── 本業 → 副業 → 活動 ── の順は固定。

> **「期間」の正規化**: ハイブリッド方式で集めた `YYYY-MM` 形式の開始年月でソートします。「現在も継続中」のエントリは「終了 = 現在」として、新しい順では最上位に並びます。

## 11. Step 4 — 書き出し

メモリ上のエントリリストを `career/work-history.md` に書き出します。

### 11.1 既存ファイルとの関係

- **`work-history.md` が存在しない場合**: `init` 未実行 ── Step 0 でチェックして案内のみで終了するべき (§13 参照)。
- **存在する場合**: §13.1 の「既存エントリの上書き警告」で同意を取った上で、既存内容を全面置換する。ヒアリングで入れたエントリを **メモリ上のリストで全置換** する形。
- **テンプレ末尾の編集ヒント (コメント) は再書き出し** する。手編集の助けになるため。
- **0 件で終了した場合は書き出しを行わない** ── 既存ファイルを保護する。これは Step 5 (§12) の挙動と合致させる。

### 11.5 共通の書き出しルール

- **見出しと値の間は空行 1 つ**。手編集しやすく、`cleanup` の検出ルールにも合致する。
- **エントリとエントリの間は空行 2 つ**。視認性のため。
- **任意項目で値が無い場合は、その `### ` ブロックごと出力しない**。「役職: (なし)」のような空欄を残さない。
- **本業の `### プロジェクト: <名前>` ブロックが 0 件のとき**: その本業エントリは PJ ブロックを書き出さない。会社単位の項目だけ書く。
- **副業・活動の見出しは内部的に統一**: 副業の「立場」も活動の「自分の役割」も、Markdown 上は `### 役職` として保存する。`### 使ったツール・スキル` / `### 成果` も同じ見出しで統一。これは `create` / `cleanup` のパースをシンプルに保つため。質問文だけカテゴリに合わせて言い換える (§7 / §8 参照)。
- **書き出すブロックにインラインコメントは付けない**: 「`### 役職` をなんて書けばいい?」と迷う手編集ユーザーのケアは、`templates/work-history.md` のファイル冒頭コメントとひな型コメントに任せる。`hearing` が書き出す各エントリには注釈コメントを足さない。理由は、編集中に削除されたり、コメントだらけで読みにくくなるのを避けるため。
- **テンプレ末尾の「新しいエントリを追加するときのひな型」コメント**: そのまま再書き出しする。手編集の助けになる。

### 11.6 書き出しの動作

1. メモリ上のエントリリストを `$ORDER` で並べ替え。
2. ファイル冒頭 (`# 職歴・副業・活動` のタイトルとファイル先頭コメント) を保持。
3. エントリ部分を全置換。
4. ファイル末尾のひな型コメント (`<!-- ■ 新しいエントリを追加するときのひな型 -->`) を保持。
5. `Write` で全体を書き出す。

> **`Write` の前に `Read` し直す**: 並行セッション対策。会話前半で読んだ記憶のまま `Write` しない。差分が予期しない大きさなら、ユーザーに確認を入れる。

## 14. 共通制約

- **プロフィール ── `config.md` / `career/profile.md` ── には絶対に触らない**。`hearing` が書き換えるのは `career/work-history.md` のみ。
- **`portfolio.html` には絶対に触らない**。HTML の再生成は `create` の仕事。
- **テンプレート (`templates/`)・スキル (`skills/`)・ドキュメント (`docs/`) には絶対に触らない**。`hearing` は cwd 側のユーザーデータだけを扱う。
- **入力 Markdown は YAML フロントマターを使わない `## 見出し` 構造** ── `cleanup` / `create` と同じ前提。
- **見出し名は固定** ── `### 種別` / `### 期間` / `### 役職` / `### やったこと` / `### 業務内容` / `### 全体の成果` / `### 使ったツール・スキル` / `### 成果` / `### プロジェクト: <名前>` / `#### 使ったツール・スキル` / `#### 成果` 以外の見出しを勝手に作らない。
- **対話文・選択肢ラベル・完了メッセージは温かいトーン**。「以下を入力してください」「を選択してください」のような事務的命令形は禁止。`CLAUDE.md` の「文体のトーン」と memory `feedback_warm-tone.md` のルールに従う。
- **仕様書のメタ用語をユーザー画面に出さない**。「正規化」「ハイブリッド方式」「フォーマット」「フラグ」「メモリ」「パース」「正規表現」のような語は **仕様書の中の説明** に使うのは OK だが、ユーザーへの質問文・選択肢ラベル・案内文には絶対に出さない。
- **ユーザー向け対話文では「フォルダ」を使う**。「ディレクトリ」「サブディレクトリ」のような用語は使わない。仕様書本文では「`./assets/`」のようにパス記法で表記しても、対話文上は「`./assets/` フォルダ」と言い換える。
- **`( )` で補足を書くスタイルをユーザー画面に出さない**。`(任意)` `(自由記入)` `(例: 〇〇)` のような表記は質問文・選択肢ラベルから一切排除する。任意性は「思いつかなければ『特になし』で大丈夫です」のような **文中** で表現する。CLAUDE.md「補足の書き方ルール」と整合させる。仕様書のメタ説明 (たとえば本文中の「(§7 / §8 参照)」のような参照) は対象外。
- **並行セッション対策**: `Write` 直前にもう一度 `Read` し、差分が想定外なら立ち止まる。会話前半で読んだ記憶のまま `Write` しない。
- **ユーザーが「やめる」「キャンセル」と言ったらすぐ中断**。中断のときの挙動は **メモリ上のエントリ件数** で分かれる:
  - **1 件以上のエントリを入力済み** ── 「ここまでに入れた $N 件、保存しますか? (はい / いいえ)」を **1 回だけ** 尋ねる。「はい」なら Step 3 (並び順の質問) を経て書き出しまで進む。「いいえ」ならメモリを破棄して終了。`work-history.md` には何も書き込まない。
  - **0 件 (まだ何も入れていない)** ── 黙って終了。`work-history.md` には何も書き込まない。
  - 10 分かけて本業 3 社を入れたあとに誤って「やめる」と言った場合に、黙って消えてしまうのを防ぐためのルール。
- **`### 種別` の値は `本業` / `副業` / `活動` の 3 つだけ**。それ以外を書き出さない。
- **性別 (gender) は扱わない** ── 古い設計の名残があっても無視。

## 15. 想定されるエラー / エッジケース

| 状況 | 対応 |
|---|---|
| `./career/work-history.md` が無い | §13 の案内のみ。何もせず終了 |
| `./assets/` ディレクトリが無い | §4.3 の案内のみ。何もせず終了 |
| `./assets/` 配下に画像が無い | §4.2 でユーザーに選択を委ねる |
| 既存 `work-history.md` に手書きエントリがある | §13.1 で **上書き警告** を出して同意を取る。同意があれば全置換、無ければ即座に終了。「既存内容を読み込んで編集モードで再開」する機能は v1 では実装しない |
| ユーザーが対話途中で「やめる」 | §14 のルールに従う。エントリ 1 件以上なら保存確認、0 件なら黙って終了 |
| 並行セッションが同じ `work-history.md` を編集した | 書き出し直前の `Read` で気づいたら、書き出しを中断してユーザーに確認 |
| `Bash ls` が失敗した | ユーザーに「フォルダの状態が読めなかったので、いったん中断します」と伝えて終了 |

## 16. このコマンドが扱わないこと

- **プロフィール (氏名・職業・連絡先・自己紹介・趣味・話せる言語など) のヒアリング** ── `config.md` と `career/profile.md` をユーザー自身に手編集してもらう前提。`init` の完了案内で促す。
- **顔写真のファイル名のヒアリング** ── `assets/` に置かれた画像を `create` 側が自動で拾う。`hearing` は「assets に画像があるか」のチェックのみ。
- **HTML 生成** ── `create` の仕事。
- **既存 Markdown の構造修復** ── `cleanup` の仕事。
- **テーマカラーやサイトタイトルのヒアリング** ── `create` の B-1.5 で必要に応じて尋ねる仕様。`hearing` ではトーン違いになるので扱わない。

---
description: 手書きで編集した入力 Markdown ── config.md / profile.md / work-history.md ── の構造的な崩れを 1 件ずつ確認しながら整える
---

このコマンドは、ユーザーが手で `config.md` / `career/profile.md` / `career/work-history.md` を編集したあとに **構造の乱れを優しく整える** 補助コマンドです。`init` でも `create` でもない、ちょっと特殊な 3 本目のメイン外コマンド。

> **このコマンドの責任範囲**: 入力 Markdown 3 つと `assets/` の整合性チェックのみ。**`portfolio.html` には絶対に触りません**。HTML を作り直したいときは、このコマンドが終わってから `/cc-portfoliokit:create` を叩いてください。

最初に以下の **短い導入** だけ表示してから Step 1 に進んでください (長文の前置きは禁止)。

```
【入力ファイルを整えます🧹】
config.md / profile.md / work-history.md をざっと見て、
ちょっと崩れているところを 1 件ずつ確認しながら直していきます。
HTML には触らないので、安心してどうぞ。
```

詳しい仕様は [`docs/specs/cleanup-command.md`](../docs/specs/cleanup-command.md) を参照。実装時はこの仕様書を **必ず読んでから** 作業を始めてください。

---

## Step 1: 状態判定

`Bash` で次のファイルの存在を確認します。

- `./config.md`
- `./career/profile.md`
- `./career/work-history.md`
- `./assets/` 配下のファイル一覧 ── `ls -la ./assets/` 程度で OK

**1 つでも入力 Markdown が欠けている場合**: 何も書き換えず、以下を出力して終了。

```
■ いまの状況: 入力ファイルが揃っていません。
  足りないもの: <欠けているパスを列挙>

先に /cc-portfoliokit:init を実行してファイル一式を作ってください。
init は何度叩いても、既存ファイルを勝手に消したりはしません (確認してくれます)。
```

**3 つすべて揃っている場合**: Step 2 に進む。

## Step 2: 全件スキャン

3 ファイルを `Read` で読み込み、仕様書 §3 の検出ルールに沿って **問題リスト `$ISSUES`** を組み立てます。

> **このステップでは `Edit` を一切呼ばない**。スキャンと修正を分離するのが安全策です。

各 `$ISSUE` は次の情報を持たせます (内部メモとして保持してください):

| 項目 | 内容 |
|---|---|
| `id` | 連番 `#1`, `#2`, ... |
| `file` | 対象ファイルパス |
| `line` | 該当行番号 (近似で OK) |
| `category` | `STRUCTURE` / `EMPTY_BLOCK` / `FORMAT` / `PARENS` / `ASSET_MISMATCH` / `WORK_HISTORY` のいずれか |
| `severity` | `high` / `mid` / `low` |
| `summary` | 1 行で表す問題内容 |
| `before` | 現在の該当箇所の抜粋 (3〜10 行) |
| `after` | 提案する修正後の姿 |
| `action` | `EDIT` (置換) / `DELETE_BLOCK` (見出しブロックごと削除) / `ADVISE` (助言のみ) |

### 検出するもの (要約)

- **STRUCTURE** (high): 必須見出しが欠けている ── 例: `## 氏名` / `## サイトタイトル` / `### 種別` ── を見つけて ADVISE。**`## キャリア総年数` は必須見出しから外れた** (新仕様)
- **EMPTY_BLOCK** (mid): 中身が空の `## 〇〇` / `### 〇〇` ブロック → 見出しごと削除提案 (DELETE_BLOCK)。ただし「必須項目で空」のものは STRUCTURE 扱いで助言のみ
- **FORMAT** (mid/low): 見出し直下の空行抜け / ブロック区切りの空行不足 / 行末空白 / HEX 形式不正 / `## 表示言語` の値が `ja`/`en` 以外
- **PARENS** (low): 値の本文中の `(例: 〇〇)` `(参考: 〇〇)` のような明示的補足記号 → 自動置換しない、ADVISE のみ
- **ASSET_MISMATCH** (mid/low): `config.md` の顔写真パスが実ファイルと食い違っている / `assets/` の使われていない画像
- **WORK_HISTORY** (high/mid/low): `### 種別` 欠落・値が想定外・複数あり / `### 期間` 欠落 / 本業の `### 業務内容` 欠落 (副業・活動は `### やったこと` 欠落) / 箇条書きでない / 旧 `### 使用技術` 表記の検出

> 検出ルールの厳密な定義は仕様書 §3 を参照。`PARENS` と `WORK_HISTORY` の値判定は **必ず ADVISE** で、勝手に書き換えないこと。

## Step 3: サマリー提示

`$ISSUES` の集計を以下の形でユーザーに出します (件数が 0 の行は省略可)。

```
🧹 cleanup スキャンが完了しました。

検出された問題: $TOTAL 件
  - config.md:              $C 件
  - career/profile.md:      $P 件
  - career/work-history.md: $W 件
  - assets/ との不整合:     $A 件

内訳:
  high  (構造の必須項目):  $H 件
  mid   (見やすさ・ルール違反): $M 件
  low   (任意の整形):       $L 件

これから 1 件ずつ確認していきます。
各問題で「直す / スキップ / 残り全部 OK / 中断」を選べます。
始めてもいいですか? (Yes / No)
```

`$TOTAL = 0` の場合は次を出力して終了 (Step 5 はスキップ):

```
✨ きれいな状態です。何もする必要はありませんでした。
そのまま /cc-portfoliokit:create に進んで大丈夫です。
```

ユーザーが `No` ── または「やめる」「キャンセル」 ── を選んだら、何もせず終了。

## Step 4: 1 件ずつ確認

`$ISSUES` を **severity の降順 (high → mid → low)** に並べ、同じ severity 内は **file 順 → line 順** で整列して、1 件ずつ提示します。

各問題の提示テンプレート:

```
─ 問題 $i / $TOTAL ─
ファイル: $file (行 $line 付近)
種類:     $category ($severity)
内容:     $summary

【今の書き方】
  $before

【こう直そうと思います】
  $after

どうしますか?
  1) 直す
  2) スキップ (このまま残す)
  3) 残り全部 まとめて Yes (※ high のみ自動修正、mid/low はスキップ)
  4) 中断 (ここまでの修正は保持)
```

### 4.1 ユーザー応答の処理

- **1) 直す**:
  1. **直前にもう一度 `Read`** して、その問題の対象箇所が会話開始時のままか確認。並行セッションで書き換わっているなら、その問題はスキップして「他のセッションが変更したようなので飛ばします」と一言伝える。
  2. `$action` に従って実行:
     - `EDIT` → `Edit` で該当行を置換
     - `DELETE_BLOCK` → 見出し行から次の同レベル以上見出しの手前までを `Edit` で削除
     - `ADVISE` → `Edit` は走らせない。「ユーザー自身に直してもらう案内」を出して次へ
  3. `Edit` 直後にもう一度 `Read` して、見出し / コメント / 空行 / 他のブロックが壊れていないか確認。
  4. 次の問題へ。

- **2) スキップ**: 何もせず次の問題へ。

- **3) 残り全部 OK**:
  - **残っている `severity: high` の問題** に対してのみ、`action` に従って自動修正を実行 ── ただし `ADVISE` は自動実行しない、ADVISE は ADVISE のままスキップ扱い。
  - **`severity: mid` と `low`** は手を付けず、スキップ扱いで残す。
  - 全件処理し終わったら Step 5 へ。

- **4) 中断**: そこまでの修正は保持。Step 5 へ。

### 4.2 失敗時の挙動

- **`Edit` の old_string が見つからない** など 1 件の修正に失敗した場合: その問題を `FAILED` として記録し、次の問題に進む。ユーザーには「自動で直せませんでした。お手数ですが手で開いて直してください」と短く伝える。
- **`FAILED` が連続して 3 件** 出たら、その時点で全体を中断 → Step 5 へ。「ファイルの状態が想定と違うようなので、いったん止めます」と伝える。
- **`Read` の結果が会話開始時と大きく違う場合** ── 並行セッションが触った可能性 ── も同様に中断する判断材料にしてよい。

### 4.3 対話文のトーン

- 専門用語禁止 ── 「ドリフト」「正規化」「リファクタリング」のような単語は出さない。
- 「**ちょっと崩れているところ**」「**整える**」「**そろえる**」のような優しい言い回しを使う。
- ユーモアを少しだけ添えても OK。ただし問題提示の正確さは絶対に削らない。

## Step 5: 完了報告

最後に以下を出力します。

```
✅ cleanup 完了

直した:    $FIXED 件
スキップ:  $SKIPPED 件
残った:    $REMAINING 件 (high $RH / mid $RM / low $RL)
```

`$REMAINING > 0` のときは続けて次を出します。

```
残課題があります。手で開いて直すか、もう一度 /cc-portfoliokit:cleanup を叩いてください。
```

`$FIXED > 0` のときは続けて次を出します。

```
変更を HTML に反映するには /cc-portfoliokit:create を実行してください。
このコマンドは HTML を作り直すところまではやりません。
```

---

## 注意 — このコマンドの絶対ルール

- **HTML / portfolio.html / templates/ / docs/ / skills/ には絶対に触らない**。書き換え対象は cwd 側の入力 Markdown 3 つと、`assets/` のチェックのみ。
- **値の意味を変える書き換えをしない**。たとえば「TypeScript」を「JavaScript」に変える、のような変更は一切しない。`cleanup` は **構造のみ** を扱う。
- **コメント `<!-- ... -->` は常に保持する**。中身に編集ヒントが入っているため。
- **`## 見出し` 行そのもの (ラベル部分) は書き換えない**。値の置換 / 空ブロック削除 / 空行調整 だけ。
- **1 件ずつの確認制を死守する**。一括書き換えは禁止 ── 「残り全部 OK」を選ばれても `severity: high` のみ自動修正、mid / low は触らない。
- **並行セッション対策**: `Edit` の直前にもう一度対象ファイルを `Read` し、最新状態に対して差分を取る。会話前半で読んだ記憶だけで Edit しない。
- **ユーザーが「やめる」「キャンセル」と言ったら即座に中断**。そこまでの修正は保持して、何が反映されたかを短く報告。
- **入力ファイルは YAML フロントマターを使わない素朴な Markdown**。`## 見出し` 直下の値の行だけを扱い、他のブロックを壊さない。

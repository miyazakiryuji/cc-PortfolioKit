---
description: 経歴 (本業・副業・活動) を対話で 1 件ずつ集めて career/work-history.md に書き出す
---

このコマンドは、cc-PortfolioKit の **経歴ヒアリング専門** のコマンドです。プロフィール ── 氏名・職業・連絡先・自己紹介・趣味など ── は聞きません。それらは `config.md` と `career/profile.md` を手編集で埋める前提です。

詳しい仕様は 3 つの仕様書に分かれています。実装フェーズに応じて必要なものを `Read` してください:

- [`docs/specs/hearing-command.md`](../docs/specs/hearing-command.md) ── 全体像 / Step 0 起動前提 / Step 1 入り口 / Step 2 メインメニュー / Step 3 並び順 / 共通制約
- [`docs/specs/hearing-categories.md`](../docs/specs/hearing-categories.md) ── §6 本業 / §7 副業 / §8 活動 のヒアリング詳細
- [`docs/specs/hearing-edit-and-write.md`](../docs/specs/hearing-edit-and-write.md) ── §9 編集サブメニュー / §11 書き出し / §12 完了報告

最初に下の **短い導入** だけ表示してから Step 0 に進んでください。長い前置きは禁止。

```
【経歴のヒアリングを始めます】
本業・副業・活動を 1 件ずつ伺っていきますね。
プロフィール (お名前や自己紹介) はここでは触らないので、お気軽にどうぞ。
```

---

## Step 0: 起動前提のチェック

まず `Read` で `docs/specs/hearing-command.md` を読み、**§13「起動前提のチェック (Step 0)」と §13.1「既存エントリの上書き警告」** に従ってください。

`Bash` で次の存在を確認:

- `./career/work-history.md` ── 必須
- `./assets/` ── 必須

`work-history.md` が無い場合は仕様書 §13 の案内のみで終了。`work-history.md` が存在しエントリ 1 件以上ある場合は §13.1 の上書き警告を出してユーザーの同意を取る。「やめる」を選ばれたら即座に終了。

---

## Step 1: 入り口の案内

`Read` で `docs/specs/hearing-command.md` の **§4「Step 1 — 入り口の案内」** に従ってください。

- §4.1 これからの流れ案内 ── 温度感メッセージを 1 度だけ表示
- §4.2 アイコン画像チェック ── `./assets/` 配下の画像を `Bash` で確認
- 画像なしの場合は §4.2.2 の選択肢を出してユーザーに進め方を選ばせる。`1)` 続行が選ばれたら `assets_missing = true` フラグをメモリに立てる
- `./assets/` フォルダ自体が無い場合は §4.2.3 の案内のみで終了

---

## Step 2: ループメニュー

ここが `hearing` の心臓部です。`Read` で `docs/specs/hearing-command.md` の **§5「Step 2 — ループメニュー」** に従って、ユーザーが「終了する」を選ぶまでループします。

### Step 2 のフェーズ管理

メモリに次のリストを保持してください。

```
$ENTRIES = []      # 全エントリのリスト。種別が混在する
$ORDER = null      # 並び順。Step 3 で確定
$ASSETS_MISSING = (Step 1 で立てたフラグ)
```

各エントリは次のような構造で持つ:

```
{
  "type": "本業" | "副業" | "活動",
  "name": "...",
  "period": "...",          # 内部で YYYY-MM 形式に揃える
  "role": "...",
  "業務内容": [...],         # 本業のみ。副業・活動は "やったこと" を使う
  "やったこと": [...],       # 副業・活動。本業の "業務内容" との内部統一は §11.5 のルールに従う
  "全体の成果": [...],       # 本業のみ。任意
  "tools": "...",          # 副業・活動。任意
  "achievements": [...],   # 副業・活動。任意
  "projects": [...]        # 本業のみ。{ "name", "tools", "achievements" } の配列
}
```

### Step 2 のメニュー表示と分岐

仕様書 §5.1 / §5.2 のメニューを表示してユーザーの選択を待つ。選択された番号に応じて次のように動く:

| 選択 | 次の動作 | 読むべき仕様 |
|---|---|---|
| `1) 本業を追加` | `Read` で `docs/specs/hearing-categories.md` を読み、**§6 本業 1 件分のヒアリング** を実行 → エントリを `$ENTRIES` に追加 → §5.1 メニューに戻る | hearing-categories.md §6 |
| `2) 副業を追加` | 同様に **§7 副業** を実行 | hearing-categories.md §7 |
| `3) 活動を追加` | 同様に **§8 活動** を実行 | hearing-categories.md §8 |
| `4) これまでに入れた本業・副業・活動を直す` | `Read` で `docs/specs/hearing-edit-and-write.md` を読み、**§9 編集サブメニュー (2 段階方式)** を実行 → 終わったら §5.1 メニューに戻る | hearing-edit-and-write.md §9 |
| `5) 終了する` | §5.3 ゼロ件チェック → Step 3 へ。`$ENTRIES` の合計件数が 0 の場合は確認ダイアログを 1 回挟む | hearing-command.md §5.3 |

「やめる」「キャンセル」「終わり」のような自然言語入力も `5)` 相当として扱う。

### Step 2 で気をつけること

- **初回 (全 0 件) のメニュー** は仕様書 §5.1 の「初回」表記に従う ── `4)` 編集メニューは表示しない、枕詞「これから経歴を 1 件ずつ集めていきますね。最初は何を追加します?」を添える。
- **質問文・選択肢ラベルは確定形のまま** ── 仕様書中の `(自由記入)` `(任意)` のような `( )` 補足は **画面に出さない**。CLAUDE.md「補足の書き方ルール」を厳守。
- 仕様書のメタ用語 (「正規化」「ハイブリッド方式」「メモリ」「フラグ」など) も **画面に出さない**。

---

## Step 3: 並び順の質問

`Read` で `docs/specs/hearing-command.md` の **§10「Step 3 — 並び順の質問」** に従って、「新しい順 / 古い順」を尋ねる。選ばれた結果を `$ORDER` に保持。

カテゴリ間 ── 本業 → 副業 → 活動 ── の順は固定。`$ORDER` はカテゴリ内の並び替えに使う。

---

## Step 4: 書き出し

`Read` で `docs/specs/hearing-edit-and-write.md` の **§11「Step 4 — 書き出し」** に従って、`career/work-history.md` を書き出します。

主な手順:

1. `$ENTRIES` を `$ORDER` で並べ替え (カテゴリ内ソート)。
2. `Write` の **直前にもう一度** `career/work-history.md` を `Read` し、並行セッションが触っていないか確認。
3. 仕様書 §11.2 / §11.3 / §11.4 の書き出し形式に従って Markdown 文字列を組み立てる ── 本業は二段構造、副業・活動はフラット。
4. ファイル冒頭のタイトルとファイル先頭コメントは保持、エントリ部分を全置換、末尾のひな型コメントも保持。
5. `Write` でファイル全体を書き出す。
6. 書き出し直後にもう一度 `Read` し、見出し / コメント / 空行が壊れていないか確認。

`$ENTRIES` が 0 件の場合は **書き出しを行わない** ── 既存ファイルを保護する。

---

## Step 5: 完了報告

`Read` で `docs/specs/hearing-edit-and-write.md` の **§12「Step 5 — 完了報告」** に従って、温かいトーンで完了を伝えます。

- `$ENTRIES` 件数の振り返り (0 件カテゴリは出力しない)
- 次のステップとして `/cc-portfoliokit:create` を推奨
- `$ASSETS_MISSING` が `true` の場合は §12.1 のアイコン画像リマインドを末尾に追記
- 絵文字は `✅` と `🖼` の 2 つだけ。`🎉` のような派手な絵文字は使わない (CLAUDE.md「絵文字を控えめに」)

---

## ユーザーが対話途中で「やめる」と言ったとき

`Read` で `docs/specs/hearing-command.md` の **§14 共通制約** の該当ルールに従ってください。

- **メモリに 1 件以上のエントリが入っている場合**: 「ここまでに入れた $N 件、保存しますか? (はい / いいえ)」と 1 回だけ尋ねる。「はい」なら Step 3 へ進んで書き出しまで実行。「いいえ」ならメモリを破棄して終了。
- **メモリが 0 件の場合**: 黙って終了。`work-history.md` には何も書き込まない。

---

## 注意 — このコマンドの絶対ルール

- **プロフィール (`config.md` / `career/profile.md`) には絶対に触らない**。`hearing` が書き換えるのは `career/work-history.md` のみ。
- **`portfolio.html` には絶対に触らない**。HTML の再生成は `create` の責務。
- **テンプレート (`templates/`)・スキル (`skills/`)・ドキュメント (`docs/`)・プラグイン側のファイル全般** には絶対に触らない。
- **`### 種別` の値は `本業` / `副業` / `活動` の 3 つだけ**。それ以外を書き出さない。
- **見出し名は固定**: `### 種別` / `### 期間` / `### 役職` / `### やったこと` / `### 業務内容` / `### 全体の成果` / `### 使ったツール・スキル` / `### 成果` / `### プロジェクト: <名前>` / `#### 使ったツール・スキル` / `#### 成果` 以外の見出しを勝手に作らない。
- **対話文は温かいトーン**: CLAUDE.md「文体のトーン」と memory `feedback_warm-tone.md` を厳守。事務的命令形を避ける。`( )` で補足を書くスタイルを画面に出さない。
- **「フォルダ」を使う**: ユーザー向け対話文で「ディレクトリ」を出さない。
- **並行セッション対策**: `Write` 直前に `Read` し直す。会話前半の記憶のまま書き出さない。
- **性別 (gender) は扱わない**。古い設計の名残があっても無視。
- **詳しい仕様は必ず仕様書 3 ファイルを参照する**。実装で迷ったら仕様書を `Read` し直すこと。
